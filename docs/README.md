# 研发流程

本项目采用规格驱动开发，并用 TDD 落实实现。

## 文档顺序

```text
业务调研
  → PRD（为什么做、为谁做、做到什么程度）
  → SDD（系统如何实现、接口与验收契约）
  → TDD（测试先行、实现、回归）
  → 集成验收
  → Release 记录
  → Git tag
```

这不是一次性瀑布流程。需求、设计和测试会随验证结果逐层回写，但每次变更必须保持追踪关系：

```text
需求编号 → 设计决策 → 验收条件 → 自动化测试 → Release 证据
```

## 文档职责

| 文档 | 回答的问题 | 不负责 |
|---|---|---|
| [PRD](./01-prd.md) | 为什么做、用户是谁、范围与成功标准 | 具体代码结构 |
| [SDD](./02-sdd.md) | 系统怎么组成、接口、数据流、安全和异常边界 | 代替测试执行 |
| [TDD](./03-tdd.md) | 如何用测试驱动实现、如何证明完成 | 定义业务目标 |
| [Release](./releases/v0.1.0.md) | 本版本交付了什么、验证结果和限制 | 重新定义需求 |

## 规则

1. 新业务需求先进入 PRD。
2. 会影响系统边界或接口的需求，必须同步更新 SDD。
3. 每个关键验收条件必须有对应测试或明确的评测案例。
4. 测试通过、Demo 可运行、已知限制清晰后才能打版本 tag。
5. 产品调研、原始资料和历史版本作为参考输入保留，不直接作为当前验收标准。
